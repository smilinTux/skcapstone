- `skcapstone deploy` takes public stacks: a manifest `stacks:` entry pins a stack repository (`stack.yaml`: tools, services in restart order, roles) to a release ref on its main, nodes take parts only through `nodes.<node>.roles`, and `nodes.<node>.stacks` pins one node to a canary ref. A config instance may carry `files.yaml` (managed `whole`, `block` and `link` files, with a duplicate-key check), validated before publish and undone with the rest. Every tools change is recorded under `~/.local/state/sk-deploy/tools-changes/` and `deploy rollback` undoes it, on tools-only nodes and before a venv switch.
- `deploy plan` shows each stack's ref, the roles, managed file diffs and the restart order without changing the node; `deploy status` shows the last tools change; `deploy drift` and `doctor` add `deploy:files` (a managed file or block edited since the last deploy, compared offline against the change record).
- Final review fixes: a node fetches only the stacks its roles take (a roleless node never depends on a stack); rollback restores only a managed block's region and keeps lines added outside it, copies an edited whole file to `~/.local/state/sk-deploy/rolled-over/` first, stops a unit the apply created before removing it, refuses after an unrecorded change, and runs without a manifest on a tools-only node; an undo that fails on the apply failure path is recorded for `deploy rollback`. `files.yaml` entries take `restart: [units]`, a changed file nobody restarts for is noted, and `deploy plan --json` reports `errors`, `restarts_complete` and `notes` at the top level.
