The GFS backup script in this repo was missing three fixes that existed only in noroc2027's deployed copy, so any node deploying from the repo got a backup whose alerts no-op under cron and that aborts after writing the tarball but before its checksum. Landed: the 2026-10-15 cron PATH guard (`command -v sk-alert` is false under cron's minimal PATH, which is why a 2026-10-14 low-disk abort reached nobody and backups sat broken for a day), tolerance of tar exit 1 (a file changing mid-read killed the run between writing the archive and writing its sha256, rotation and off-site push), and the `~/.hermes` config slice (that directory is not a git repo and was in no backup set despite holding the Talk and Telegram wiring and the cron job definitions; config and logic only, ~3.6 MB, secrets excluded by name because the off-site push sends the archive to another host). Retention depths are now overridable from `config/backup.env`: noroc2027 was running 7 daily and 5 weekly against defaults of 14 and 8 while the header still advertised 14, so an edited script was both hiding the real depth and how these fixes came to exist on one machine and in no repo. `~/.hermes` is added as a tar operand only when it exists, since naming a missing path makes tar exit 2 and most chi nodes have no Hermes.
